# TrustGate v0.1 scope

## Purpose

TrustGate is a sensitive-data protection layer between user or backend data, LLMs, and tools. It controls the representation and release of sensitive data, not whether an action is authorized.

> TrustGate governs data exposure, not action authorization.

## Responsibility boundary

```text
Agent / framework proposes a tool call
                |
                v
TrustGate: sanitize, tokenize, apply data-release policy,
           rehydrate approved values, sanitize results, audit
                |
                v
Existing tool runtime: IAM, approval, business validation, execution
```

TrustGate may transform arguments for both read and write-style destinations, such as `get_account`, `update_customer`, or `send_email`. It makes no determination about whether the surrounding system should execute any of them.

## Data-release policy

Policy is destination-aware and default-deny:

```yaml
version: 1
data_policies:
  ACCOUNT_NUMBER:
    external_llm: tokenize
    destinations:
      get_account: allow
      update_account: allow
      send_email: deny
```

The v0.1 tool-bound decision is `ALLOW` or `DENY` for a combination of sensitive data type and destination. It must not infer a decision from whether a tool is read-only or write-like.

See the [policy reference](data-release-policy.md) for the complete schema,
strict YAML validation, default-deny behavior, and the sample decision matrix.
Policy does not extend detection or authorize token-free calls.

## Session and vault lifecycle

Every interaction uses an explicit `TrustSession`. Token mappings are process-local, in-memory, session-scoped, and ephemeral. They are never intentionally persisted to a database, cache, filesystem, audit store, log, or remote service.

Tokens include an independent random 32-hex vault namespace, preventing reuse
across process lifetimes. Old unnamespaced tokens are rejected as malformed.
Cross-type overlapping detection spans fail closed with `DetectionUnavailableError`;
same-type spans may be merged without dropping release restrictions.

Closing a session makes mappings unavailable. Process loss also makes mappings unavailable and rehydration must fail closed. TrustGate does not claim guaranteed physical memory zeroization.

Method failure does not automatically close a session or undo previously created
private state. Use `with gate.session()` or close in `finally` so failures also
discard vault mappings, entity/mention state, aliases, and token ownership.
An audit failure while opening a session clears the partially created state.
Close discards private state before its audit attempt and remains closed if
that attempt raises a fixed `AuditRecordingError`.

## Diagnostics and local example

Presidio diagnostic logs are suppressed in the current detection context during
initialization and analysis, including DEBUG logs with normalized context.
Logger levels and unrelated threads remain unaffected.

Audit events contain only fixed safe metadata and opaque identifiers. Per-person
resolution entries expose a state and reason, not names, normalized values,
candidate lists, or alias configuration. Supported tool-result failures record
safe categories; exceptions do not retain the original resolver/detector message
or exception chain. An audit allowance means data release, not tool execution.

Argument traversal also rejects cycles, unsupported objects, custom scalar
subclasses, and unexpected iterator errors with `ToolArgumentRehydrationError`.
Result sanitization rejects custom scalar subclasses rather than returning
objects with custom representations. Ordinary shared JSON containers remain
supported. Audit callback/serialization failures use `AuditRecordingError`
without retaining unsafe exception chains, including a body exception when
close auditing fails during context exit. Already accepted safe events are not
rolled back; custom callbacks remain trusted host code.

Transcript collection is opt-in per session and disabled by default. It records
only successful sanitized inputs/results, using session-owned in-memory copies
and independent snapshots. It does not record raw inputs/results, rehydrated
tool arguments, LLM responses, or alias/vault state. Audit and transcript history
can remain readable after close without access to discarded raw mappings.
Undetected sensitive content can still appear in sanitized returns and therefore
in an enabled transcript; coverage must be verified for the application's data.

The [local example](../examples/boundary_demo.py) uses synthetic fixtures,
mock LLM/tools, and the installed English model. It makes no external LLM calls
or real writes. Its fixture-specific output checks are not a general detector.

## Conservative person resolution

Only locally detected PERSON spans enter identity resolution. Exact normalized
full names establish session-local candidates. First-name mentions, titled
surnames, and direct given-name aliases may reuse an existing identity only
when all candidate producers together identify exactly one eligible entity.
Aliases never override conflicting exact or partial matches. The English name
order and complete remaining components are used; fuzzy matching, reverse alias
inference, and transitive alias inference are not implemented.

Each entity has an independent ID and an immutable canonical tool value.
Unresolved and ambiguous mentions receive separate token identities and cannot
become candidate identities. Repeated identical uncertain surface forms keep
their tokens and states even after later input. Earlier confirmed occurrences
also keep their identities if a later mention becomes ambiguous.

Caller-provided alias additions are validated and copied when a session is
created, supplement the built-in relations, and are cleared on close. They are
not stored on TrustGate, persisted, audited, logged, or sent to an LLM. Mention
history contains only offsets, token entity IDs, states, and safe reasons.

Resolution does not prove a real-world identity or detect every sensitive
mention. Unknown spellings may be missed by NER, and aliases do not extend the
detector vocabulary. An ambiguous token can release only its original surface
value after an explicit policy ALLOW, not a guessed full name. The host retains
responsibility for tool execution and business validation.

## Out of scope

Authentication; IAM; RBAC/ABAC user permissions; tool or business authorization; human approval; write-action approval; transaction authorization; idempotency; retries; durable workflow state; persistent vaults; distributed sessions; and agent framework integrations.

User-response rehydration remains explicitly unavailable.

## v0.1 local acceptance

The documented v0.1 implementation and all six Day 7 verification steps are
complete as of 2026-10-22. Package version 0.1.0 retains its pre-alpha status.
See the [final acceptance report](day7-acceptance.md) and
[release notes](../CHANGELOG.md) for evidence and behavior changes.

The verified installation/test environments are Windows AMD64 with Python
3.11.17 and 3.14.6 and local English model `en_core_web_sm` 3.8.0. Other platforms,
Python versions, and dependency-minimum combinations are unverified. Local
acceptance does not establish production readiness or universal detection
coverage, and is not a third-party security audit.
